## Жёсткие требования организаторов (нарушение = дисквалификация)

1. Агент читает документ требований, переданный при запуске (PDF обязательно; DOCX, MD, TXT — дополнительно). Содержание
   документа не зашито в код и не подменяется своим ТЗ.
2. Одна команда: путь к файлу требований и путь к файлу отчёта. Отчёт формирует агент, а не человек.
3. Отчёт на русском: паспорт прогона (документ, дата, модель, версия агента = git-коммит); таблица нарезки «ID в отчёте —
   ID в документе — краткая формулировка» (свои ID + цитата, если номеров нет); проверка каждого требования; проверка
   набора; сводка (число требований, нарушений, критичные дефекты: непроверяемые, противоречивые, неполные); итог (можно ли
   начинать разработку и тестирование, что исправить первым). Ни одной общей фразы без ссылки на место в документе.
4. README: как получить ключ, куда положить, команда запуска, куда ляжет отчёт. `.env.example` без секретов; секреты не в Git.
5. Критерии — ISO/IEC/IEEE 29148:2018 п. 5.2.5, 5.2.6 и IEEE Std 830-1998 п. 4.3.

## Стратегия по критериям жюри

| Критерий (25 %) | Чем выигрываем | Как показать за 30 секунд |
| :--- | :--- | :--- |
| Уточнение требований | Clarification Engine: вопрос привязан к требованию и дефекту, объясняет «зачем» и риск, даёт 2–4 варианта (не факты); статусы открыт/уточнён/отклонён; ответ попадает в отчёт и пересчитывает показатели | ответить на вопрос в панели → счётчик и отчёт обновились |
| Архитектура | правила + LLM, 8 модулей, параллельные шаги, строгие JSON-схемы, сверка цитат, скептик-перепроверка, смена модели в `.env`, 31 тест без ключа | схема из README + «неверная цитата → требует проверки» |
| Ценность | реальные метрики прогона; вердикт готовности; бот и API для процесса банка; история в Postgres | бот присылает вердикт по файлу из чата |
| Презентация | Document Lens: документ сканируется лучом, дефекты прикрепляются к строкам; демо-режим; материалы защиты | живой прогон документа организаторов |

## Архитектура (минимально достаточная)

Один оркестратор, модули: Document Parser → Requirement Extractor → (детерминированные правила ‖ Quality Auditor ‖
Consistency Auditor ‖ Completeness Auditor ‖ FinTech Risk Auditor) → Evidence Grounding → Clarification Engine →
скептик-перепроверка → Scoring Engine → Report Generator. Правило: всё, что решается регулярным выражением или структурой,
решается без LLM (размытые слова, «и/или», единицы денег, пустые поля, заглушки, HTTP-семантика, коды статусов, типы
параметров, дубли, отсутствие версии и приоритетов). LLM — только смысл.

## Защита от галлюцинаций (обязательно)

1. Ответ модели — JSON по Pydantic-схеме (Claude: принудительный tool call). Невалидно → повтор с текстом ошибки → безопасный отказ.
2. Каждая цитата ищется в документе (точно / нечётко ≥ 82 %) и заменяется дословным фрагментом; строку и страницу считает агент.
3. Нет совпадения → «требует проверки»; несуществующий ID → отбросить; ID документа (Ф-2) → ID отчёта.
4. CRITICAL/HIGH от модели проверяет независимый «скептик»: keep / downgrade / reject.
5. Молчание документа — пробел документа, а не отсутствие функции в продукте.
6. Без успешного LLM-анализа готовность не может быть READY — только INSUFFICIENT DATA.

## Каждое замечание

что обнаружено · где (строка, страница, раздел, ID) · дословная цитата · почему проблема (критерий + пункт стандарта или
«экспертная рекомендация») · риск · как исправить · улучшенная формулировка (неизвестные числа — `<уточнить: …>`).
Критичность не завышать: CRITICAL — блокирует реализацию/приёмку или риск денег/ИБ; HIGH — до разработки; MEDIUM — риск
интерпретации; LOW — улучшение; INFO — наблюдение. Фиктивных нарушений ради количества нет.

## FinTech

Сначала применимость (yes/no/unknown), потом покрытие (covered/partial/missing). Неприменимое — N/A, не дефект.
Аспекты: платежи, суммы и валюты, минимальные единицы и округление, повторная доставка, идемпотентность, дубли, тайм-ауты,
ретраи, ошибки провайдеров, возвраты, статусы операций, конкурентность, аутентификация, разграничение доступа, аудит,
ПДн и платёжные данные, недоступность внешних систем, согласованность данных, восстановление.

## Каналы

* **CLI** — главный путь сдачи. Прогресс этапов, коды выхода 0/1/2, создание директорий.
* **REST API** (FastAPI) — загрузка, SSE-прогресс, результаты, отчёты, PATCH статусов вопросов, токен доступа.
* **LÜMEN Intelligence** (React + TS + Vite + Tailwind + Recharts + React Flow + Framer Motion) — светлая банковская тема,
  белые поверхности, синий/голубой, умеренный фиолетовый только для «вопросов». Разделы: Обзор, Новый аудит, Требования,
  Дефекты, Граф связей, Вопросы владельцу, FinTech-риски, Отчёты, Настройки. Без пустых кнопок и фейковых страниц.
* **Telegram-бот** — файл → прогресс → вердикт, главные дефекты, кнопки вопросов и отчёта.
* **Хранение** — локальные файлы по умолчанию; Supabase (Postgres, RLS) для постоянной истории с откатом на локальное.
* **Деплой** — Railway по Dockerfile, healthcheck `/api/health`, коммит из `RAILWAY_GIT_COMMIT_SHA`.

## Definition of Done

- [ ] `pytest` зелёный без ключа (Mock LLM): PDF, DOCX, пустой, битый, без ID, неоднозначность, противоречие, дубль,
      неполнота, нет критериев приёмки, API-контракт, мало данных, ошибка API, невалидный JSON, отчёт, выдуманные цитаты.
- [ ] `npm run build` без ошибок; все страницы открываются без ошибок консоли.
- [ ] Реальный прогон на документе организаторов сильной моделью; отчёт проверен глазами: цитаты совпадают, строки верные.
- [ ] Паспорт отчёта содержит чистый коммит (без `-dirty`).
- [ ] Демо помечено как демо везде.
- [ ] В README — ограничения, честно.
