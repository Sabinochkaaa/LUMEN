# LÜMEN — материалы для презентации и защиты

## Структура выступления (5–7 минут)

1. **Проблема (30 с).** Дефект в ТЗ, найденный после старта разработки, — это переписанный код, повторное
   тестирование и сдвиг релиза. Ревью требований сегодня ручное, зависит от опыта и не оставляет следов.
2. **Решение (30 с).** LÜMEN — аудитор требований: документ на входе, через минуты — отчёт с доказательствами,
   вердикт готовности и вопросы владельцу продукта. CLI, веб-панель, API и Telegram-бот на одном ядре.
3. **Живое демо (3 мин)** — сценарий ниже.
4. **Архитектура (1 мин).** Правила + LLM, 8 модулей, параллельные шаги, строгие JSON-схемы, защита от галлюцинаций.
5. **Ценность (30 с).** Метрики прогона, интеграция в процесс банка (бот, API, история в Supabase).
6. **Что дальше (15 с).** Jira/Confluence-коннекторы, сравнение версий ТЗ, обучение на решениях аналитиков.

## Сценарий демо

1. Открыть **Новый аудит**, перетащить `docs/requirements.md` (документ организаторов). Показать, как линза
   сканирует документ и проходят 15 этапов.
2. **Сводка:** вердикт NOT READY, индекс качества, число критичных дефектов. Нажать на отмеченную строку в линзе:
   замечание открывается с цитатой, риском и улучшенной формулировкой.
3. **Дефекты → противоречие:** критерий приёмки про покупку 31 января, проведённую 1 февраля, против Ф-2
   («месяц определяется по дате совершения покупки»). Показать обе цитаты с номерами строк.
4. **Дефекты → API-контракт:** сохранение через GET, ответ 200 с телом ERROR при наличии 400, amount — integer в
   запросе и string в ответе, раздел 403 описывает 404.
5. **Граф связей:** красные рёбра противоречий, требования без критериев приёмки.
6. **Вопросы владельцу:** выбрать вариант ответа, нажать «Уточнить» — счётчик открытых вопросов и показатели
   пересчитываются, ответ попадает в отчёт.
7. **FinTech-риски:** идемпотентность повторной доставки, тиыны и тенге, N/A для неприменимого.
8. **Отчёт:** скачать Markdown, открыть HTML. Паспорт прогона: модель, дата, коммит агента.
9. **Telegram:** отправить боту тот же файл — вердикт и HTML-отчёт приходят в чат.

## Ответы на вероятные вопросы жюри

* **«Модель может выдумать замечание?»** Каждая цитата сверяется с документом программно; несовпадающие помечаются
  «требует проверки», несуществующие ID отбрасываются, CRITICAL/HIGH проходят перепроверку скептиком. Номера строк
  считает агент, а не модель.
* **«Зачем правила, если есть LLM?»** Правила дешёвые, мгновенные и воспроизводимые: одинаковый результат при каждом
  прогоне. LLM тратится только на смысл. Без ключа агент всё равно полезен и честно ставит INSUFFICIENT DATA.
* **«Почему не мультиагентная система?»** Один оркестратор с модулями проще отлаживать и объяснять; параллельность
  есть там, где она даёт выигрыш по времени.
* **«Индекс качества — это ISO?»** Нет, это прозрачная формула LÜMEN, описанная в отчёте; стандарты задают критерии.
* **«Какая модель?»** Любая: Claude, Gemini (бесплатно), OpenAI-совместимые, локальные через OpenAI API. Смена — в `.env`.
* **«Как это внедрить в банк?»** API и бот встраиваются в процесс согласования ТЗ, история хранится в Postgres
  (Supabase), ключи — только на сервере, доступ к API закрывается токеном.
